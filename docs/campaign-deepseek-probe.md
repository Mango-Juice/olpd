## 후속 원인 추적 — 같은 날 재검증

**이전 “남은 3건 의미 실패” 표현을 정정한다.** 실제로는 같은 원문 `빈 코르크 상자를 물에 띄우고 그 위에 올라 건너편 발판에서 내려`의 세 반복이었다. 모두 `push → wait(afloat=true) → board → wait(landingReachable=true) → dismount`를 반환했다.

오프라인 실행에서는 선행 push 뒤 환경 갱신으로 이미 afloat=true다. 추가 wait는 행동 0개, 세계 tick·위치·driftAge·탑승 상태를 바꾸지 않았다. 허용형은 호출/tick `1/1, 2/2, 3/2, 4/3`, 생성형은 `1/1, 2/1, 3/2, 4/2, 5/3`으로, 행동열과 최종 물리 상태·완료가 같다. 기존 오라클은 3~4개 노드와 landing wait 하나만 허용하므로 5개 노드/대기 두 개를 거절했다. `physics.pass=false`도 이 형식 제한을 포함했으며 실제 클리어 실패가 아니었다.

원문 “띄우고”에는 뜬 상태를 만든 뒤라는 결과 의미가 있다. 프롬프트에는 `float` 동사가 없고 공개 `afloat` 상태가 있으며, 사건을 wait/if로 보존하라고 한다. 모델이 결과 확인으로 세분한 표현은 방어 가능한 해석이다. **직접 원인은 오라클의 좁은 정규형, 배경 원인은 프롬프트와 평가기의 행동 완료·결과 확인 계약 불일치**다. 이 사례로 모델 능력 부족을 입증할 수 없다.

추가 대기는 세계에서는 0틱이지만 UI revision/저장 한 번을 늘린다. 현재 실행 예약 기준 기본 1.3초·빠르게 450ms·움직임 줄이기 100ms가 추가될 수 있다. 따라서 물리 의미와 표현 간결성·재생 지연을 별도 평가해야 한다. 수정 후보는 안전하게 증명되는 no-op 대기만 정규화하거나 평가에서 허용하는 것이다. 일반 wait를 무조건 지우거나 점수를 올리려고 전부 허용해서는 안 된다.

## 앱 적용 및 반복 조율

사용자의 후속 요청에 따라 `/api/campaign-interpret`에 실제 DeepSeek를 연결했다. 프롤로그·1장의 Jev 경로는 유지한다. 기본값은 **non-thinking**, `temperature: 0`, 한 요청당 API 한 번, 8초 제한이다. `CAMPAIGN_DEEPSEEK_THINKING=low`는 명시적으로만 켤 수 있으며 자동 재시도나 thinking 승격은 없다. 전체 장 구현 goal은 중단 상태를 유지하고 배포하지 않았다.

- 공개 속성만 모델에 제공하고, AST 구조·대상·주체·속성·범위를 로컬 검증한다. 생성 결과는 항상 사용자 확인을 거친다. 근거 없는 confidence를 만들지 않는다.
- 500자 입력 제한, 중복 제출 차단, 취소 버튼, 연결 종료 시 upstream 취소를 적용했다. 해석 오류·취소는 노트 작성 기회를 소모하지 않는다. 공급자가 이미 처리한 요청의 과금 취소를 보장하는 것은 아니다.
- 탑승/하차, 목적어·출발지 방향, 모호한 물체와 역할, 꺼짐/부정 조건, 병렬 유지의 종료 조건을 조율했다. 위험한 세 칸 붓기는 안전한 두 칸으로 고쳐 주지 않고 실제 과적 실패가 나야 정답이다.
- “발판에 닿으면 내려”를 표현할 수 있도록 기존 실제 거리·도달 범위에서 계산하는 공개 `landingReachable` 상태를 추가했다. 물리 성공 조건을 완화하거나 해법을 모델에 전달하지 않는다.

### 최종 v6 실측

27개 입력 × 3회 = **81회 중 78회**가 의미·물리 기대값을 모두 충족했다. 평균 **0.963초**, 중앙값 **0.953초**, p95 **1.248초**, 최대 **1.560초**다. p95는 nearest-rank이며 로컬 서버에서 공급자 응답 완료·검증까지의 시간이다. 장시간 운영의 지연 보장은 아니다.

남은 3건은 동일한 도입 원문에서 명시하지 않은 `afloat=true` 대기를 추가한 경우다. 세 번 모두 실제 구간은 완료했지만, 현재의 좁은 의미 동치 기준에 들어오지 않아 실패로 남겼다. 임의 대기 삽입이 일반적으로 안전하다고 가정하거나 정답 기준을 넓혀 점수를 높이지 않았다. 조건·부정·협동 종료·명료화 사례는 이번 최종 반복에서 기대값과 일치했다.

이 최종 81회만의 추정 비용은 **$0.023480**(약 $0.000290/회)다. 아래 공식 peak 단가와 응답 usage로 계산했으며, 앞선 조율 호출·브라우저 호출을 포함한 총비용이나 실청구액은 아니다. 원본: `artifacts/campaign-deepseek-live/2026-09-22T02-29-00.418Z/cohort.json` (`campaign-deepseek-6`).

로컬 적용 후 플레이테스트를 계속할 수준으로 판단한다. reasoning은 기본으로 켜지 않는다. 78/81을 전체 입력 정확도나 모든 장의 완료 증거로 사용하지 않는다.

### 평가와 한계

실제 production adapter를 `scripts/evaluate-campaign-deepseek-live.ts`로 호출한다. 27사례는 고정 8문장, 어순·수량·출발지 변형, 조건/부정/대기, 7장 병렬 협동, 모호함·없는 대상·규칙 변경 요청, 적용 범위를 포함한다. 실제 stage executor와 scheduler로 결과를 확인한다. 7장 사례 통과는 7장 제품 구현 완료를 뜻하지 않는다.

이 데이터로 프롬프트를 조율했으므로 최종 점수는 **조율 코호트의 반복 회귀 결과**이며 미지의 전체 한국어 입력에 대한 정확도가 아니다. 4~6장 전체 자연어와 8~10장 관측 참조·보스는 이번 실측 범위가 아니다.

평가 기준도 별도로 검증했다. 원문의 종료 조건 생략은 실패이며, 단순 도입의 “발판에서 내려”에는 하차 직전의 정확한 접안 대기만 동치로 허용한다. 이 경우 실제 실행에서 조건 참·행동 0·tick과 world 불변을 요구한다. 동일 주체의 물리적 동시 행동 충돌은 무료 명료화 또는 정확한 충돌 프로그램으로만 허용한다. 초기 잘못된 오라클을 고친 기록과 이전 raw 결과는 보존했다.

### 조율 이력

- v1: 26개 중 21개(당시 기준). 하차를 move로 해석하거나 모호한 물체/역할을 임의 선택하는 문제를 확인했다.
- v2: 81회 중 72회(당시 기준). “꺼짐”을 과하게 되묻는 문제와 표현 불가능했던 도착 조건을 확인했다. 일부 실패는 앞서 설명한 오라클 오류였다.
- v3: 81회 중 72회(당시 기준). 3건은 접안 대기의 동치 오라클 교정 전 채점이며, 협동 종료 조건 누락 6건은 실제 의미 오류다.
- v4: 협동 2사례 × 3회는 6/6. 이어 전체 평가의 12번째 요청에서 `wait`를 action verb로 생성해 로컬 구조 검증이 차단했다. 당시 평가기는 provider 코드에 중단해 11/12로 끝났다. 앱에서 재시도하거나 잘못된 프로그램을 실행하지 않았다.
- v5: 81회 중 77회. 도착 조건에 요청하지 않은 move를 추가한 2건, 종료 사건 없는 유지에 임의 until을 추가한 2건이 의미 검사에서 실패했다. 해당 초기 상태에서 이동은 실행되지 않았고 동일 주체 충돌은 물리 검증이 차단했으나, 의미 오류를 성공으로 세지 않는다. wait 노드와 until 행동의 문법 차이를 명시했다. 평가기는 응답을 받은 뒤 구조 검증에 실패한 사례를 실패로 기록하고 다음 독립 사례를 계속 평가한다. 전송 장애·rate limit에서는 중단한다.

- v6: 자율 이동의 도착 사건을 별도 이동 명령으로 바꾸지 않도록 하고, 종료 사건 없는 유지와 동일 주체의 동시 역할 충돌을 명시했다.

`pnpm test`: 34파일 335개 통과. `pnpm build`: 타입 검사·빌드 통과(기존 500kB 번들 경고). 보안/실패 테스트는 숨은 속성 제외, 비정상 JSON/AST, 과대 응답, 8초 timeout, 업로드 뒤 연결 종료, 공급자 오류 비노출·재시도 없음 등을 포함한다.

재현: `pnpm run eval:campaign -- --repeat=3`, `pnpm run test:campaign:browser`. 실제 API 비용이 발생한다. 키와 인증 헤더, 내부 reasoning 원문은 산출물에 기록하지 않는다.

브라우저 산출물: `artifacts/deepseek-v6-browser-campaign-deepseek.json` 및 같은 접두사의 PNG. 초기 8사례 비교는 아래에 당시 조건 그대로 남긴다.

## 평가 방법

- `scripts/evaluate-campaign-deepseek.ts`는 기존 Jev 고정 8사례의 문장·초기 세계·정답 기준을 복사한 별도 평가기다. 기존 Jev 스크립트와 운영 provider는 수정하지 않았다.
- 공개 entity 설명·물성·위치·actor 상태만 제공한다. 정답 AST, stage complete 함수, 힌트, 기대 결과는 API 입력에 넣지 않는다.
- 일반 행동 역할과 AST 계약으로 지침 전체를 한 번에 JSON으로 받는다. JSON mode 이후 로컬 `parseProgram`으로 구조를 검증한다. JSON mode 자체를 JSON Schema 강제 보장으로 주장하지 않는다.
- 같은 system prompt를 두 모드에 사용했으며 prompt hash와 실제 요청/응답 content·usage·model·finish reason·지연을 artifact에 보존했다. 요청 사이 정답 피드백이나 자동 재시도를 하지 않았다. 내부 reasoning 원문은 저장하지 않는다.
- 이번 8사례는 단순 순차 지시이므로 action/sequence 이외의 제어 노드를 먼저 거절한다. parallel/if/until을 평탄화해서 정답으로 오인하지 않는다. 조건·협동 검증은 이후 실제 scheduler로 별도 해야 한다.
- intro 원문의 push/place 물리적 동등성 허용은 기존 기준과 같다. 위험 사례는 단순 safe=false만으로 통과시키지 않고 실제 outcome=failure를 요구한다.
- Jev 교정 후 2/8과 비교할 수 있는 것은 동일 문장·세계에 대한 해석 경로의 결과다. Jev의 4단계 Choice/Noul과 DeepSeek의 1회 JSON 생성은 prompt/프로토콜이 달라 모델만을 통제한 실험은 아니다.
